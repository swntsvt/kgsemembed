# #143 artefacts

- `padding_drift.json`, `padding_drift.md`: padded vs unpadded embedding
  differences per model, generated by `scripts/padding_drift.py` (MPS, pinned
  model revisions). Regenerate one model per process:

  ```bash
  for m in M1 M2 M4 M5; do venv/bin/python scripts/padding_drift.py --model $m --n 256; done
  venv/bin/python scripts/padding_drift.py --model M3 --n 32
  ```

## Notes

- Texts are encoded as the pipeline encodes sources: `role="source"` (M5's
  instruction prefix applied) through `EmbeddingEncoder`, whose batch size
  shrinks for long texts. The table's Batch column is effective / configured.
- M3 uses 32 longest + 32 random texts: an unpadded M3 encode of 512 texts
  creates enough distinct batch shapes to exhaust MPS memory, which is the
  problem bucketed padding solves. Its effective batch is 1, so its row
  measures only the pad-to-64 tokens, not mixed-length batches. M3 does not
  run on D4 in any condition (C14 D5, C15 D1); these texts only stress its
  8,192-token limit.
- M4's two texts above 1e-6 are short (36 and 39 tokens; 8.96e-5 and
  1.80e-5). Two padded M4 encodes of the same 512 texts are bitwise
  identical, so the difference is a deterministic effect of padding, not
  run-to-run noise. Its mechanism in BioLORD (MPNet) is not established.
- Re-running the script reproduces every row exactly. An earlier ad-hoc
  sample (length ties broken differently, M5 without its prefix) gave M5
  2.2e-6, so the maxima depend on the sample.
- Every stored result was produced with padding on, so no compared pair
  differs by this effect.
